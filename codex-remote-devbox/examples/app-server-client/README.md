# Service-side App Server client

A small TypeScript transport example for a trusted service calling one Devbox.
Node 24 runs these files directly using built-in type stripping. `ws` connects
directly to that Devbox over plain WebSocket. The supported
protocol subset was checked against bindings generated by Codex **0.162.1**.
This is an example integration, not a published SDK or a durable job scheduler.

## Install and validate

```bash
cd codex-remote-devbox/examples/app-server-client
npm ci --ignore-scripts
npm run typecheck
npm test
```

Tests use an HTTP/WebSocket fixture on loopback. They make no Codex, provider,
or model calls. Development
dependencies are only needed for type checking/tests; the runtime needs `ws`.

## Connection smoke (does not start work)

After a separately approved deployment, run this from a device on the tailnet:

```bash
export CODEX_APP_SERVER_URL=ws://codex-devbox-2:8787/
npm run smoke
```

The URL is the only connection setting. Use the device's full MagicDNS name if
the short name is unavailable. The existing Tailscale-exposed Service selects
only Devbox 2, so reconnecting returns to its persistent state. Cluster clients
can use `ws://codex-devbox-2.codex-devbox.svc:8787/` for the same endpoint.

This endpoint has no application token or TLS configuration. It uses the
existing Tailscale network access, with no new caller-specific rules. Any client
that can reach it can control this Devbox. Redirects are not followed.

`smoke.ts` initializes, sends `initialized`, and requests `thread/list` with
`useStateDbOnly: true` to avoid rollout metadata scan/repair. It prints neither
thread contents nor server configuration. `node integration-smoke.ts` additionally
tests two concurrent clients, `config/read`, and a new initialized connection
after disconnecting one client. Both commands stop before creating threads or
turns. The latter is intended for isolated image smoke fixtures.

`node proxy-smoke.ts` is another isolated-fixture check: run it as the Codex user
over SSH after the managed daemon starts. It opens `codex app-server proxy` and
performs HTTP Upgrade/WebSocket over its stdio, then initializes and reads config.
The proxy relays raw socket bytes, so JSON-lines input is not valid for this
subcommand. Supplying the connection environment above additionally checks the
network client while that SSH proxy connection stays open. Both paths finish
without creating a thread or model turn; cleanup flushes the WebSocket close
frame and ends stdin before waiting for the byte-proxy process to exit.

## Use from application code

`client.ts` exports `AppServerClient`, `RpcError`, and `OutcomeUnknownError`.
`request<T>()` is an escape hatch for additional version-appropriate RPCs. The
small declared return types intentionally cover only fields this example uses;
they do not replace generated protocol bindings or runtime business validation.

The following is application integration code; `jobs` and `ui` are adapters you
provide for durable storage and user interactions. Executing the turn below
starts real agent work and can consume provider quota.

```ts
import { AppServerClient, RpcError } from './client.ts';

const endpoint = {
  url: 'ws://codex-devbox-2:8787/',
};
const client = await AppServerClient.connect({
  ...endpoint,
  experimentalApi: true, // request_user_input is currently experimental.
  onNotification(event) {
    // Filter by the thread/turn belonging to your job; don't log raw payloads.
    ui.updateProgress(event);
  },
  async onServerRequest(request, signal) {
    switch (request.method) {
      case 'item/tool/requestUserInput': {
        // Render questions/options and return the actual answer for each question id.
        // Example wire result: { answers: { market: { answers: ['Canada'] } } }
        const answers = await ui.askQuestions(request.params, signal);
        return { answers };
      }
      case 'item/commandExecution/requestApproval':
      case 'item/fileChange/requestApproval': {
        // Only send an explicit user decision. Display available decisions accurately.
        const decision = await ui.askApproval(request.params, signal);
        return { decision };
      }
      default:
        // Permission requests, MCP elicitations, and dynamic tools each need their
        // own schema/handler. Unknown methods never receive automatic approval.
        throw new RpcError(-32601, 'Unsupported server request');
    }
  },
});

try {
  const { thread } = await client.startThread({
    cwd: '/workspaces/rewards',
    sandbox: 'read-only',
    approvalPolicy: 'on-request',
    approvalsReviewer: 'user',
  });
  // Store the originating Devbox BEFORE starting a turn.
  await jobs.saveThread(jobId, { ...endpoint, threadId: thread.id });
  // Persist a "starting" state before sending; a missing reply is not a failed start.
  await jobs.markTurnStarting(jobId);
  const started = await client.startTurn(thread.id, 'Research the Canadian version of this card.');
  await jobs.saveTurn(jobId, started.id);
  const finished = await client.waitForTurn(thread.id, started.id);
  if (finished.status !== 'completed') {
    await jobs.markNeedsAttention(jobId, finished.status);
  } else {
    // The RPC turn is finished; validate the actual research/Curation result next.
    await jobs.verifyResearchResult(jobId);
  }
} finally {
  client.close(); // Closing the connection does not interrupt the running agent.
}
```

The underlying client replies to the **same server request id**, so answering a
clarification continues the existing turn. A question written only as ordinary
assistant text is different: send a new turn with the answer on the same thread.
The abort signal fires when `serverRequest/resolved` clears a pending request or
the transport disconnects; the UI should dismiss that prompt and not submit a
stale answer. Keep the connection alive while awaiting human input. The client
does not treat optional automatic-resolution timers as permission to approve.

The sample sets a read-only sandbox deliberately. Selecting a different sandbox,
permission profile, tools, and trusted repositories belongs to the application;
the direct endpoint gives access to the trusted Devbox without per-thread
authorization. Avoid simultaneous Desktop/service control of the same thread;
use separate threads and serialize business mutations per thread.

## Continue, steer, cancel, and reconnect

After one turn completes, `client.startTurn(savedThreadId, answer)` starts the next
turn of the same conversation. During a turn, use
`client.steerTurn(threadId, expectedTurnId, extraInstruction)`; to cancel, use
`client.interruptTurn(threadId, turnId)` and wait for `turn/completed` with
`status: "interrupted"`. A request acknowledgement is not task completion.

On reconnect, create a **new** initialized client with the saved Devbox endpoint,
then call `client.resumeThread(savedThreadId)`. Thread state belongs to that
Devbox's persistent home. Keep the saved Devbox endpoint and thread id together;
do not resume against another Devbox. Do not repeat `initialize` on the old connection.

`OutcomeUnknownError` means a request or turn deadline expired or the connection
failed. The client never retries automatically: `turn/start` may already have
started a model/tool call. Read `thread/read` metadata and page
`thread/turns/list` after resuming to reconcile persisted work, active turns,
and the saved turn id before deciding whether to send more input. If the start
reply was lost, compare server history with the stored pre-send job state and
resolve ambiguity; do not blindly create another turn. An event may have been
missed while disconnected, so waiting only for the next completion event is not
sufficient recovery. Reconnecting alone does not guarantee re-delivery of a
pending clarification; reconcile pending server requests or interrupt/restart a
turn deliberately when recovery cannot be established.

Completion events arriving before the start reply are retained in a bounded
128-entry cache. Call `waitForTurn` promptly; use persisted thread history for
older results. The default request deadline is 30 seconds and the default turn
wait is 30 minutes. A turn wait deadline does not cancel work, so the business
scheduler needs its own timeout/cancellation policy.

Protocol reference: [official OpenAI App Server documentation](https://learn.chatgpt.com/docs/app-server).
Recheck the generated bindings and run compatibility smoke tests whenever the
pinned Codex version changes.
